## 1. Diagnóstico

### A) El móvil emparejado no aparece en el servidor propio (5038)

**Cómo busca `serve` el móvil hoy (código leído):**

1. `serve.go:103-124`: crea `adb.Runner{Path, ServerPort: 5038}` y llama a `findKnownPhone(ctx, runner, serial, addrs, deviceWait=45 s, …)`. `addrs` son `candidateAddrs` (`phone_watch.go:33-49`): `cfg.Address` (lo guarda `adbuddy connect` o `setup --connect`), la IP:puerto de Tailscale y, con el modo remoto, IP:5555. Con un emparejamiento por QR en casa no suele haber ninguna.
2. `connect.go:215-250` (`findKnownPhone`): con direcciones, mira primero `adb devices` del 5038 y prueba cada dirección (`tryAddr`); sin ellas, va directo a `findPhone`.
3. `setup.go:586-597` (`findPhone`): con serial `adb-<serie>-<sufijo>._adb-tls-connect._tcp`, llama a `pairing.Connect(ctx, runner, guid, 45 s, autoConnectWait=20 s, 1 s)`.
4. `pairing.go:400-453` (`Connect`/`connectService`): sondea `adb devices` **del 5038** cada segundo buscando el guid (o la dirección que conectó); a partir de 20 s pide `adb mdns services` **al 5038** y hace `adb connect <ip:puerto>` del servicio `_adb-tls-connect._tcp` de ese guid, repitiendo cada 5 sondeos. Si a los 45 s no hay nada: `pairing.ErrTimeout` → `adb.ErrNoDevice` → `serve.go:121-124` `DEVICE_NOT_FOUND` (exit 75), con el texto `err.serve.device_not_found_2` («ningún móvil en estado `device` en el puerto 5038…») o, si se probaron direcciones guardadas, `err.serve.device_not_found`.
5. Todo `adb` del host va al 5038: `adb.go:39-52` quita del entorno `ANDROID_SERIAL`, `ANDROID_ADB_SERVER_PORT`, `…_ADDRESS` y `ADB_SERVER_SOCKET` y pone el puerto propio. **El host nunca mira el 5037**: ni `adb mdns`, ni `adb devices`, ni nada.

**Reproducción con el adb falso (hecha):** el test nuevo `TestServeFindsThePhoneThroughTheSystemServer` (Tarea 2) con la vía nueva desactivada (`ConnectAlso(..., nil)`) reproduce el hallazgo: el 5038 no lista nada por mDNS y `serve` acaba así:

**Qué está demostrado y qué es hipótesis:**

- **Demostrado (código):** si el mDNS del 5038 no lista el servicio `_adb-tls-connect._tcp` del guid en 45 s, `serve` falla con `DEVICE_NOT_FOUND` aunque el 5037 lo vea; `adbuddy connect <ip:puerto>` lo arregla porque guarda `cfg.Address`, que el siguiente `serve` prueba primero (paso 2).
- **Deducido del hallazgo:** como `adbuddy connect` funcionó con el 5037 en marcha, el móvil acepta la conexión del 5038 (con la clave de adb compartida, `~/.android/adbkey`). Si el 5038 hubiera listado el servicio, `connectService` habría hecho el mismo `adb connect` a los 20 s. Lo que falló es el **descubrimiento mDNS del 5038**, no la conexión.
- **Hipótesis (sin probar; validaciones 44-45):**
  - **H1, dos servidores compitiendo por mDNS en Windows.** Ambos adb (backend Openscreen) se atan al UDP 5353 con `SO_REUSEADDR` (`client/openscreen/platform/udp_socket.cpp`, `MdnsBind`). Las respuestas multicast deberían llegar a los dos, pero las unicast (o lo que Windows reparta entre sockets reutilizados) solo a uno.
  - **H2, backend o versión distintos.** El adb de ADBuddy (platform-tools 37, Openscreen) y el del sistema pueden usar backends o interfaces distintos (Bonjour frente a Openscreen; adaptadores virtuales de Hyper-V o WSL).
  - **H3, servidor propio recién arrancado.** El 5037 llevaba horas en marcha y ya tenía el servicio en caché. El 5038 arrancó con `serve` y depende de respuestas a sus consultas, que un móvil en reposo puede perder (filtrado de multicast con la pantalla apagada).
- **Veredicto: hueco de diseño, no de seguridad.** La spec (tabla de casos límite: «Otro servidor adb en marcha | … así que no hay conflicto») da por hecho que el servidor propio ve lo mismo que el del sistema, y el hallazgo lo desmiente. El comportamiento es el documentado (`DEVICE_NOT_FOUND`, arreglo `adbuddy connect`), pero no es aceptable como experiencia por defecto: con Android Studio abierto es el caso común.

### B) Código de salida 127 al cerrar

- **Demostrado (código):** el host no tiene ningún camino propio que salga con 127. `errors.go:13-17` define 0, 1, 2, 75, 78 y 130 (y 126 en el shim y las ayudas); `ExitCode` (`errors.go:131-145`) solo devuelve esos o el de `exitCodeError`. `ExitWith` se usa en `doctor.go:207` (1) y en `run.go:88`, que **reenvía el código del agente** en `adbuddy run`. `serve` devuelve `nil` (0) cuando se cierra mientras sirve (`serve.go:251-258`), y lo fija `serve_test.go:311` (`code != 0` falla). Antes de servir, Ctrl+C da 130 (`Interrupted`, fijado en `serve_test.go:359`). En Windows, cerrar la ventana con la X llega como `SIGTERM`, por la misma vía, y si Windows mata el proceso el código es `0xC000013A`, no 127.
- **Hipótesis (validación 47):** 127 es el «command not found» de un shell. Lo más probable es que sea el estado del shell o del lanzador que mostró el terminal al cerrarse (Windows Terminal escribe «process exited with code N» con el último estado de bash, y en Git Bash un comando inexistente deja `$? = 127`), o que el usuario arrancara el agente con `adbuddy run` y fuera el agente (o su envoltorio) quien salió con 127.
- **Veredicto: aceptable / del lanzador.** No hay cambio de código. Cómo comprobarlo: validación 47.

## 2. Decisiones

- **Ruling: preguntar al servidor adb del sistema (solo lectura) la dirección que anuncia el guid emparejado, cuando el propio no la ve; no limitarse a documentarlo.** Por qué: arregla el síntoma con H1, H2 y H3 (en las tres el 5037 lo ve, que es el estado del hallazgo) sin que la persona tenga que leer la IP y el puerto en el móvil. Qué cuesta si me equivoco: si el 5037 tampoco lo ve, la vía no hace nada (una consulta TCP local de como mucho 2 s cada ~5 s dentro de la espera de 45 s) y queda `adbuddy connect` como hoy.
- **Ruling: protocolo de adb por TCP (`host:mdns:services`), no `adb -P 5037 mdns services`.** Por qué: el programa adb arranca un servidor si no hay ninguno y **mata el del puerto si su versión no es la suya**, lo que tiraría el adb de Android Studio. El protocolo (`OKAY` + 4 dígitos hex + texto) está comprobado en AOSP (`adb.cpp` `handle_mdns_request` → `SendOkay(fd, s)` = `OKAY` + `SendProtocolString`; `adb_io.cpp`). Qué cuesta si me equivoco: si una versión futura cambia la respuesta, `HostQuery` falla y todo queda como hoy (no rompe nada).
- **Ruling: solo con guids que permiten comprobar la identidad (`pairing.GuidSerialNo` ok).** Por qué: un móvil hallado por mDNS con guid sin número de serie hoy se acepta sin comprobar (`checkFound` → `Verified=false` y un aviso). No se amplía eso a una segunda fuente. Qué cuesta si me equivoco: los móviles con `ro.serialno` «unknown» o corto no se benefician y siguen con `adbuddy connect`.
- **Ruling: solo en `findPhone` (`serve`, `setup` con móvil ya emparejado, `remote off` sin `serve`); no en el vigilante (`phone_watch.go`) ni en el primer `pairing.Connect` de `setup` tras emparejar.** Por qué: es el cambio mínimo que cubre el hallazgo. Qué cuesta si me equivoco: una reconexión a mitad de sesión con puerto nuevo sigue dependiendo del mDNS del 5038 (validación 49, pendiente).
- **Ruling: sin textos nuevos para la persona; la vía es silenciosa y la documentación la explica.** Por qué: la consigna es no tocar los catálogos, y el resultado se ve igualmente («ADBuddy is serving <ip:puerto>»). Qué cuesta si me equivoco: la persona no sabe que se consultó su adb. Los textos opcionales están en §6.
- **Ruling: no guardar en `config.toml` la dirección hallada por el 5037.** Por qué: hoy `serve` no guarda direcciones halladas por mDNS (solo `connect` y `setup --connect`), y el puerto cambia al reactivar la depuración. Qué cuesta si me equivoco: el siguiente `serve` repite la espera de ~20 s.

func fakeServer(t *testing.T, answer func(req string) []byte) (string, <-chan string) {
	t.Helper()
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { ln.Close() })
	reqs := make(chan string, 16)
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) {
				defer c.Close()
				var h [4]byte
				if _, err := io.ReadFull(c, h[:]); err != nil {
					return
				}
				n, err := strconv.ParseUint(string(h[:]), 16, 16)
				if err != nil {
					return
				}
				req := make([]byte, n)
				if _, err := io.ReadFull(c, req); err != nil {
					return
				}
				reqs <- string(req)
				c.Write(answer(string(req)))
			}(c)
		}
	}()
	return ln.Addr().String(), reqs
}

```go
package adb

import (
	"context"
	"errors"
	"fmt"
	"io"
	"net"
	"strconv"
	"time"
)

// SystemServer is where the adb server of the person's own tools listens
// (adb's default port), as opposed to ADBuddy's private one.
const SystemServer = "127.0.0.1:5037"

// errNotAnswer means what came back is not an adb server's answer.
var errNotAnswer = errors.New("not an adb server answer")

// HostQuery sends one host request (such as "host:mdns:services") to the adb
// server listening at addr and returns its answer. It speaks adb's own
// protocol over TCP instead of running the adb program: it never starts a
// server where none listens, and never restarts one of another version (the
// adb program kills a server whose version is not its own). Nothing listening
// is an error. The whole exchange is bounded by ctx; when ctx ends, the
// error is ctx's.
func HostQuery(ctx context.Context, addr, req string) (string, error) {
	if req == "" || len(req) > 0xffff {
		return "", fmt.Errorf("a host request has 1 to 65535 bytes, not %d", len(req))
	}
	var d net.Dialer
	conn, err := d.DialContext(ctx, "tcp", addr)
	if err != nil {
		return "", ctxOr(ctx, err)
	}
	defer conn.Close()
	stop := context.AfterFunc(ctx, func() { _ = conn.SetDeadline(time.Unix(1, 0)) })
	defer stop()
	if _, err := io.WriteString(conn, fmt.Sprintf("%04x%s", len(req), req)); err != nil {
		return "", ctxOr(ctx, err)
	}
	var status [4]byte
	if _, err := io.ReadFull(conn, status[:]); err != nil {
		return "", ctxOr(ctx, err)
	}
	switch string(status[:]) {
	case "OKAY":
		s, err := readProtocolString(conn)
		return s, ctxOr(ctx, err)
	case "FAIL":
		return "", fmt.Errorf("the adb server at %s refused %s", addr, req)
	}
	return "", errNotAnswer
}

// readProtocolString reads 4 hex digits of length and that many bytes.
func readProtocolString(r io.Reader) (string, error) {
	var h [4]byte
	if _, err := io.ReadFull(r, h[:]); err != nil {
		return "", err
	}
	n, err := strconv.ParseUint(string(h[:]), 16, 16)
	if err != nil {
		return "", errNotAnswer
	}
	buf := make([]byte, n)
	if _, err := io.ReadFull(r, buf); err != nil {
		return "", err
	}
	return string(buf), nil
}

// ctxOr is ctx's error once ctx ended, else err.
func ctxOr(ctx context.Context, err error) error {
	if err != nil && ctx.Err() != nil {
		return ctx.Err()
	}
	return err
}
```

## 7. Riesgos

- **Un proceso local que escuche en 127.0.0.1:5037 y mienta** puede mandar al 5038 a hacer `adb connect` a una IP:puerto que él elija. La exposición es la misma que hoy con mDNS (cualquiera en la red puede anunciar el guid): el móvil se verifica antes de usarlo y uno ajeno da `WRONG_PHONE` y se desconecta. Un atacante con código local ya tiene más poder que este. Mitigación: solo 127.0.0.1, solo el guid exacto y solo guids verificables.
- **Dos conexiones al móvil** (la del 5037 y la del 5038): ya ocurre con `adbuddy connect`, que funcionó en el hallazgo (validación 46).
- **Tiempo:** la primera consulta llega a los 20 s (`autoConnectWait`), igual que hoy el `adb connect` explícito; cada consulta tiene un tope de 2 s y no alarga la espera de 45 s.
- **Tests:** un test que no pase por `TestMain` de `cli` no existe (la variable es del paquete). `cmd/adbuddy` (e2e) no usa seriales de guid.
- **Hipótesis sin confirmar:** si la causa real fuera otra (por ejemplo, que el 5037 tampoco lo listara y lo tuviera conectado por otra vía), la vía no hace nada y no empeora nada. Las validaciones 44-45 lo dirán.
- **`setup` por QR con el 5037 en marcha:** si H1 se confirma, emparejar por QR (que usa el mDNS del 5038 para `_adb-tls-pairing._tcp`) podría fallar igual. No está cubierto (validación 48).
